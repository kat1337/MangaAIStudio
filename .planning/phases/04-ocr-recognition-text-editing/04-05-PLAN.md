<objective>
Deliver the inline text editor (TEXT-04, D-05/D-06/D-07/D-08): double-click a box → a transient QGraphicsProxyWidget wrapping a QTextEdit appears ON the box rect (inset 2px so the border stays visible); the user edits the current-focus field (translation if present, else recognized); Enter or click-away commits via the PageBox setter and pushes a BOXES snapshot; Esc cancels. While active, single-click/move/resize are disabled. The vertical toggle (D-06) is a v1 no-op fallback per RESEARCH Pitfall 5 — payload.vertical is preserved as export metadata but the editor always renders horizontal. This is the first QGraphicsProxyWidget in the project; the canvas dispatch gets a new top-priority branch (RESEARCH Pitfall 3 — the inline-editor-active guard must precede all other mouse dispatch).

Purpose: TEXT-04 is "edit the recognized OCR text inline in a box" — the inline editor IS that surface. The Inspector (Plan 04) is the secondary edit home for the non-focus field; the inline editor is the primary edit surface for the focus field. Per UI-SPEC §15, QGraphicsProxyWidget(QTextEdit) wins over QGraphicsTextItem-in-edit-mode (full cursor/selection/IME for Japanese input + frame/background control). Per RESEARCH Pitfall 3, the proxy has documented focus/IME quirks — the canvas mouse-press dispatch MUST check "inline editor active? click outside it?" before any other dispatch, and commit + consume. Per RESEARCH Pitfall 5, vertical CJK editing is non-trivial in Qt and ships as a documented horizontal-only fallback.

Output: InlineEditor + canvas double-click dispatch + commit/cancel semantics + GUI tests, all green. OCR itself (Plan 06) is what fills the text the user edits here — this plan ships the edit surface against already-populated boxes.
</objective>
