1. **Resize does nothing** (UAT re-test 1). Click a box → 4 amber corner handles appear → click+drag a corner handle → the box does NOT resize. The 03-06 fix enlarged the corner hit area (correct, stays) but was not sufficient.

## Proven facts (these are RELIABLE — trust them)

- **The handler code is correct in isolation.** `_select_and_begin_move` arms `_moving_box`; the move branch in `mouseMoveEvent` computes a scene delta and calls `setRect`; `_advance_resize` recomputes the rect with the opposite corner anchored and calls `setRect`; `_commit_resize` finalizes. All verified to mutate `rect()` correctly when called directly offscreen.
- **`current_box()` reads `self.rect()`** (box_item.py), and `boxes_snapshot()` materializes PageBoxes from `current_box()`. So the snapshot/persistence read path is keyed on `rect()`.
- **The canvas `mousePressEvent` accepts-and-returns early for box clicks** (canvas.py ~859-880): a click on a `CornerHandle` → `_begin_resize` + `event.accept()` + `return`; a click on a `BoxItem` → `_select_and_begin_move` + `event.accept()` + `return`. It does NOT call `super().mousePressEvent()` for these. This is deliberate (the comment at ~877 explains the fall-through for the empty-canvas/mask case).
- **`pos()` vs `rect()` divergence is real for QGraphicsRectItem** — proven: a BoxItem at `rect=(10,10,30,30)` + `setPos(40,40)` leaves `rect()` unchanged and `current_box()` returns the stale `(10,10,40,40)`. (This proof is valid mechanics, but see the trap below about whether the live move actually uses `pos()`.)

## The bug is in LIVE EVENT DELIVERY, not the handlers

Every offscreen probe (including the previous session's, and the 30 existing GUI tests) calls the handlers **directly** — `_select_and_begin_move(...)`, `_advance_resize(...)`, `item.setRect(...)`. These probes **pass**. The live app **fails**. Therefore the defect is in how Qt actually delivers press/move/release events to the canvas `QGraphicsView` in the running app, NOT in the handler bodies.

**You cannot reproduce these two bugs with direct handler calls. Stop trying.** The test suite's 260-green status is meaningless for these two symptoms.

## TRAPS TO AVOID (the previous session fell into all of these)

1. **DO NOT diagnose from offscreen probes that call handlers directly.** This is exactly what produced two wrong diagnoses. If your test calls `_begin_resize` / `_advance_resize` / `_moving_box.setRect` directly, it CANNOT see the live bug. A valid regression test MUST drive real Qt press/move/release event delivery (e.g. `QTest.mousePress/Move/Release` on the viewport with proper widget/scene coordinate mapping, or `QApplication.sendEvent` with `QMouseEvent`/`QGraphicsSceneMouseEvent` to the view/scene such that the canvas's own `mousePressEvent`/`mouseMoveEvent` are invoked by Qt — not called directly).

2. **DO NOT assume `BoxItem.ItemIsMovable` is the root cause.** The previous session concluded this confidently, removed the flag (commit 2eae32e), and it **broke the live move that was working** — reverted in a3678c4. `ItemIsMovable` is load-bearing for SOMETHING in live event delivery (likely: it keeps Qt delivering `mouseMoveEvent` to the view for the held button after the early `event.accept(); return` in `mousePressEvent`). Removing it is NOT the fix. The `pos()`/`rect()` divergence proof is valid Qt mechanics, but there is NO evidence the live move actually routes through `pos()` — that was an inference, and the live-app failure mode is still unknown.

3. **DO NOT trust the executor's "ItemIsMovable is inert offscreen" finding as evidence it's inert live.** It being inert offscreen is consistent with the broader fact (handlers called directly bypass Qt). It tells you nothing about the live app.

4. **DO NOT add a regression test that calls handlers directly and call it a guard for these bugs.** It will pass and provide false confidence, exactly as `test_boxitem_does_not_set_itemismovable` did before it was deleted.

## What a correct diagnosis probably needs

Either:

- **An interactive/instrumented approach.** Add temporary logging at the top of the canvas's `mousePressEvent`, `mouseMoveEvent`, `mouseReleaseEvent` (log which branch fires, `_resizing_box`/`_moving_box` state, the event's `buttons()`/`isAccepted()`), run the live app, and have the user perform the failing resize/move. The log will show whether `_moving_box`/`_resizing_box` arm, whether move events arrive, and whether `setRect` is reached. This is the fastest reliable path. Coordinate with the user (they offered to run the app).
- OR a **real-event GUI test** using `QTest` event delivery to the actual view widget, with the offscreen Qt platform, that reproduces the failure. This is harder to get right but automatable. The previous session's executor tried 5 approaches and couldn't trigger the failure offscreen — but a fresh attempt with a different angle (e.g. ensuring the viewport has focus, mouse tracking, proper grab) may succeed.

## Likely (UNVERIFIED) hypotheses to test — do not treat as diagnosis

- The early `event.accept(); return` in `mousePressEvent` (canvas.py ~871) may prevent Qt from establishing a mouse grab on the view, so subsequent `mouseMoveEvent`s are not delivered while the button is held — leaving `_resizing_box`/`_moving_box` armed but never advanced. (This would explain why the handler code is right but the live drag is a no-op.) If true, the fix is about event delivery / grab, not the handlers.
- For persistence specifically: it's possible the live move DOES update `rect()` correctly (via `_moving_box.setRect`), but the persistence seam reads state at the wrong time, or `_moving_box` is never armed because the press never reached `_select_and_begin_move` in the live app. Do not assume `pos()` divergence — verify what actually happens.
- `ItemIsMovable` may be what keeps move events flowing after the early return; its presence being required for move to work is consistent with the grab hypothesis above.
