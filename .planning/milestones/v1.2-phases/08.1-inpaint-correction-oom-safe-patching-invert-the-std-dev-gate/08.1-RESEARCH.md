## User Constraints (from CONTEXT.md)

### Locked Decisions
- **D-01:** The std-dev gate is INVERTED relative to Phase 8: a box is AI-inpainted (LaMa) when its border std dev is ABOVE the threshold (complex/uniform-to-the-model region); a box is median-color FILLED when its border std dev is at or BELOW the threshold (uniform region). This matches `panelcleaner/image_ops.py:705` (`pick_best_mask` fails above `mask_max_standard_deviation` → inpaint path; succeeds below → mask/fill path) and `panelcleaner/config.py:828-900` (Inpainter section).
- **D-02:** The threshold remains the existing `mask_max_standard_deviation` (default 15) surfaced by the same "Std dev threshold" control; only the side of the gate that each behavior applies to is swapped. Hand-painted (manual plane) strokes are ALWAYS inpainted regardless of the gate (unchanged contract).
- **D-03:** The Inpaint (C) action does both passes in one flow: (1) median-color fill of every Auto/Fill low-std box text-mask, (2) LaMa inpainting of the composite of (a) high-std Auto boxes, (b) Inpaint-override boxes, (c) manual-plane strokes, minus erase. Both results are baked into the page image as ONE undo entry (like today's Inpaint). Fill is not live at detect/recompute time — it applies at Inpaint time.
- **D-04:** The inpaint_override vocabulary becomes four values, persisted in `.mas` as `inpaint_override`:
  - `none`/absent = **Auto** — fill if std ≤ threshold, inpaint if std > threshold
  - `fill` — force the median-color fill regardless of std (even on a complex box; user's explicit choice)
  - `always` — force LaMa inpainting regardless of std (even on a uniform box)
  - `never` — leave the text entirely (no fill, no inpaint)
  The Inspector combo becomes Auto / Fill / Inpaint / Never (replacing Auto / Always / Never) with the existing Mixed sentinel for multi-select. The `"fill"` value is new — `.mas` load/save, save-loop emission, and the compose/fill split must all handle it. Legacy files with only the old vocabulary load unchanged.
- **D-05:** Max LaMa input size is a user setting (UI input box in settings/preferences, saved in the profile/INI) with a default of **2048×2048** pixels. If the whole page fits within the max size, the whole page is passed to LaMa (no patching).
- **D-06:** For larger pages, build patches around the regions to inpaint: each patch is the mask bbox grown to at least 25% of the image (per side), with a ~10% margin around the mask on every side that has room, capped at the max size.
- **D-07 (edge refinement):** The 10% margin applies ONLY where the image has space — a mask at the page edge gets the patch clamped to the page boundary on that side (no margin there; mask fully included, never deferred for edge proximity).
- **D-08:** A mask whose bbox crosses a patch edge in the INTERIOR (non-page-edge) case is excluded from the current patch and collected into a deferred list; subsequent patches are built around the deferred masks until every mask is covered. Each patch is inpainted independently and composited onto the page; the run produces ONE undo entry.
- **D-09:** Batch Detect+Clean and Batch Clean adopt the same corrected gate and the same patched inpainting (consistency with interactive quality; this closes the Phase 8 UAT item on batch quality matching interactive).

## Summary

Phase 8 shipped the std-dev gate **inverted** relative to vendored PanelCleaner: `compose_auto_binary` (detection_boxes.py:357-394) contributes a box's mask to the auto plane when `std_dev <= threshold` — i.e. uniform boxes get AI-inpainted and complex boxes are skipped. PanelCleaner's own semantic (image_ops.py:704-705) is the opposite: `pick_best_mask` returns `best_mask=None` **above** `mask_max_standard_deviation` and the failed fit is routed to **inpainting**; a successful uniform fit is color-filled with the mask's border **median color** (masker.py:104,138 → `combine_best_masks` + `paste`). This phase inverts our gate to match, splits Inpaint (C) into a one-shot fill+LaMa flow under a single undo entry, adds the `"fill"` override value (combo becomes Auto/Fill/Inpaint/Never), and makes the LaMa side memory-safe via patch-based inpainting with a user-configurable max input size (default 2048×2048).

The OOM premise is **confirmed by the installed dependency source**: `simple_lama_inpainting`'s `SimpleLama.__call__` passes the **full-resolution** image and mask to the LaMa UNet (only mod-8 symmetric padding; no tiling, no downscale), so a 6000×4000 page creates float32 tensors and full-res first-layer activations on the order of several GB — a real OOM on mid-range GPUs and constrained CPU setups. Patching is therefore mandatory, not defensive. The `_run_inpaint_task` worker (main_window.py:4937-4964) is where the LaMa call happens (already off the GUI thread), and SimpleLama is fully convolutional, so arbitrary patch crops are valid model inputs — the patch loop needs no model changes.

Everything this phase builds is a composition of **already-vendored or already-exported primitives**: `compose_auto_binary` (to flip), `PageBox.inpaint_state` (to re-derive), `ops.convert_mask_to_rgba`/`masker.py` paste pattern (the fill), `ops.compose_masks`/`grow_mask` (patch composition), `TorchLamaModel.inpaint` (the model seam), `compute_mask_bbox` (union bbox for the single undo entry), and the snapshot-as-geometry contract (`canvas.boxes_snapshot()`). No new external packages are required; the recommended new code is one headless module (`core/inpaint_patching.py`) plus small edits to existing seams.

**Primary recommendation:** Ship the gate flip and the fill as pure headless functions on the existing `detection_boxes.py` seam (extend `BoxMaskFit` with the fit-time `median_color`), add one new headless, Qt-free/torch-free module `core/inpaint_patching.py` for patch planning + compositing, thread a `max_inpaint_size` from the profile INI through `_dispatch_batch`/`batch_runner`, and deliberately re-base the Phase 8 tests that encode the old gate direction (they are expected breakage, not regressions — flagged per-file in §Common Pitfalls).

**Primary recommendation:** One new headless module for patching + gate-flip edits on existing seams; no new dependencies; deliberate re-base of the ~6 test files that assert the old gate direction.

### Pattern 3: Patch-based OOM-safe inpainting (new headless module)

**What:** When `page > max_size`, plan patches around the inpaint-eligible mask's regions so each model call is bounded, then composite results into one page copy. SimpleLama is fully convolutional — arbitrary crop sizes are valid inputs.

**When to use:** Every LaMa call in this phase (interactive `_run_inpaint_task` and the batch clean branch) funnels through `TorchLamaModel.inpaint`. The patch module must be importable by the batch worker → **headless purity lock applies** (source-token scan for `PySide6`/`torch`/`gui.` + hermetic subprocess probe, mirroring `test_detection_boxes_module_is_headless` at tests/test_core/test_detection_boxes.py:96-124).

**Recommended API:**
```python
# manga_ai_studio/core/inpaint_patching.py  (NEW — pure numpy/PIL, no Qt, no torch)
def plan_patches(
    mask_binary: np.ndarray,          # (H, W) uint8 — the composite inpaint mask
    max_size: tuple[int, int],        # (max_w, max_h) from profile, default (2048, 2048)
    min_context: float = 0.25,        # D-06: grown to ≥25% of page dims per axis where room
    margin: float = 0.10,             # D-06: ~10% margin around the mask where room
) -> list[tuple[int, int, int, int]]  # page-coord patch rects (x1, y1, x2, y2), ordered
```
- **Region source:** the composite mask's connected components (or per-box origin records — planner's choice; label via `cv2.connectedComponents` or simple flood fill; `cv2` is available).
- **Per region:** grow its bbox to `max(bbox_dim, 0.25*page_dim)` per axis where room then add a 10% margin of the patch size on sides with space; clamp to page bounds (D-07 edge rule: no margin where the region touches the page edge — never deferred for edge proximity); cap at `max_size`.
- **Deferral (D-08):** when building the patch for region A, any OTHER region whose bbox intersects the patch boundary in the interior is excluded from this patch and pushed to the deferred list; loop until every region is covered.
- **Patch loop:** for each rect → `patch_img = page[y1:y2, x1:x2]`, `patch_mask = mask[y1:y2, x1:x2]` → `model.inpaint(patch_img, patch_mask)` → composite back into the page copy **only where `grow_mask(patch_mask, isolation)` is set** (the model modifies a few pixels outside the mask — PanelCleaner documents this with `inpainting_isolation_radius = 5` [VERIFIED: panelcleaner/config.py:835]); later patches win in overlaps (regions are disjoint by construction).
- **Return:** the full-page result + the UNION bbox of all patch rects (drives the single undo entry + the bbox-region composite in `set_image_from_numpy`).
- **Memory-safe ordering:** exactly one patch crop + one model call live at a time; the union-bbox slice for the undo push is taken from the pre-run page on the GUI thread (bounded by page size, same order as today's full-page flow).

### Pattern 4: Combined one-shot flow with a single undo entry (D-03)

**What:** `inpaint()` keeps its current dispatch shape (GUI thread extracts payloads, worker runs, main thread applies + pushes ONE history entry). Only the worker payload grows.

**Current worker contract** — [VERIFIED: manga_ai_studio/gui/main_window.py:4964]: `return {"image": result_rgb, "bbox": bbox}` where `bbox` is `compute_mask_bbox(mask_binary)` → `(x, y, w, h)` [VERIFIED: main_window.py:6564-6565]. The finish handler pushes ONE undo entry [VERIFIED: main_window.py:5058]: `self.history.push_image_action(x1, y1, original_patch_numpy)` where the patch is the pre-inpaint slice `pre_inpaint[y1 : y1 + bh, x1 : x1 + bw].copy()` (:5021) — with the patch flow, `bbox` becomes the **union of all patch rects** (or of the single whole-page rect when no patching) and `result_rgb` is the full-page array (unchanged pixels are pixel-exact outside the union bbox by construction). `set_image_from_numpy` composites only the bbox region [VERIFIED: canvas.py:922-924]. The mask consumption stays `consume_mask_display()` (CR-04/CR-16 contract, main_window.py:5050).

**Inpaint-mask split (worker inputs):** from `boxes_snapshot()` + planes: build (a) the fill spec — list of `(mask_pil, color, x, y)` for Auto-low-std + `"fill"` boxes, (b) the inpaint binary — `compose` of Auto-high-std + `"always"` boxes ∪ manual plane, minus erase (numpy, `(manual_bin | auto_bin) & ~erase_bin` semantics, mirroring canvas.recompose_mask at canvas.py:582-612). Empty-mask branches: fill-only pages skip LaMa entirely; inpaint-only pages skip the fill; both empty → passthrough unchanged.

### Anti-Patterns to Avoid
- **"Fixing" the Phase 8 tests to minimize churn:** the gate flip deliberately inverts behavior asserted by existing tests (§Common Pitfalls 1). The tests must be re-based to the CONTEXT D-01 semantics with the authority cited, not silently weakened.
- **Recomputing the median color in the worker:** the fill color must be the fit-time `MaskFittingResults.median_color` (already off-white-rounded); a fresh `border_std_deviation` call on a box-cropped mask samples a different border and can round differently.
- **Passing the whole page to LaMa "because it usually fits":** SimpleLama has NO size guard; the cap must be enforced defensively in the worker (a page that "usually fits" on a dev GPU can OOM on the user's machine — the whole point of D-05).
- **Emptying the auto plane to make room for the fill:** fill is NOT displayed in the overlay at detect/recompute time (D-03) — but the auto plane must still show what C will **inpaint** (the LaMa half), or the overlay silently shrinks with no explanation; the will-fill signal moves to the border pens.
- **One undo entry per patch:** D-03/D-08 mandate ONE entry — the union bbox push must happen once in `_on_inpaint_finished`, never per patch.

## Common Pitfalls

### Pitfall 1: The gate-flip will break a cluster of existing tests — treat it as deliberate re-basing, not regression
**What goes wrong:** `test_core/test_detection_boxes.py` (e.g. `test_derive_per_box_fits_store_gate_lifted` asserts a textured box "does NOT contribute to the auto binary at that threshold"), `test_core/test_box_model.py` (`inpaint_state` matrix), `test_gui_border_states.py` (`_ALL_STATES = ("will_inpaint", "gate_skipped", "forced", "never")` at :54), `test_gui_inspector_override.py` (3-value combo), `test_core/test_project_io.py` (override validation), `test_core/test_batch_runner.py` (clean semantics), `test_gui_detection_settings.py` (threshold tooltip copy) all encode the OLD direction.
**Why it happens:** Phase 8 shipped the inverted gate; its tests lock the inverted behavior and the suite is green (879/879 at 08-VERIFICATION.md:115).
**How to avoid:** Plan a dedicated re-basing task per file that flips the expectations to D-01 semantics with the CONTEXT cited in the test docstring (the 01-07 gap-closure discipline: real vendored functions, no monkeypatch). The scoreboard must call this out as expected churn, distinct from the new tests.
**Warning signs:** A "fix" that changes the fixture so the box crosses the threshold the other way — hiding the semantic flip instead of asserting it.

### Pitfall 2: SimpleLama has no internal size cap — the OOM is real
**What goes wrong:** A 6000×4000 page passed whole → float32 image+mask tensors (~288 MB input alone) plus full-res first-layer activations (several GB with the 32–64-channel first conv) → OOM/swap thrash on mid hardware.
**Why it happens:** `SimpleLama.__call__` → `prepare_img_and_mask(image, mask, device)` with NO `scale_factor` and only `pad_img_to_modulo(..., 8)` symmetric padding [VERIFIED: installed site-packages simple_lama_inpainting/utils/util.py:53-70; models/model.py:28-29]. The model is fully convolutional (resolution-agnostic) so nothing rejects a huge input — it just exhausts memory.
**How to avoid:** The D-05 cap must be enforced in the worker (interactive + batch both), with whole-page fast-path when `max(h, w) <= max_size` and patch fallback otherwise. Never trust "it fits on my machine".
**Warning signs:** Batch clean of a single big page slows to a crawl or the process dies mid-run; the progress bar stalls at "Inpainting…".

### Pitfall 3: Patch seams and the model halo
**What goes wrong:** Compositing a patch result with the razor mask leaves a visible boundary: LaMa modifies a few pixels *around* the mask ("the inpainting model modifying a few pixels outside of its dedicated region" — PanelCleaner's `inpainting_isolation_radius = 5` comment [VERIFIED: panelcleaner/config.py:890-894]).
**How to avoid:** Composite each patch result only where `grow_mask(patch_mask, isolation)` is set (isolation ≈ 4–6 px), so adjacent patches' halos overlap and cover the seam. Patches are per-region (per box mask), regions are disjoint, so later-writer-wins in a halo overlap is safe.
**Warning signs:** Thin seams or ghost boundaries along the box outline after a multi-patch run on a large page.

### Pitfall 4: Mod-8 symmetric padding at the page edge (D-07 interplay)
**What goes wrong:** A mask flush against the page edge gets a patch clamped at that edge; SimpleLama pads symmetric, mirroring the mask outward into the padded margin — the model treats the mirrored mask as mask and regenerates right at the page border.
**Why it happens:** `pad_img_to_modulo` pads with `mode='symmetric'` [VERIFIED: installed site-packages simple_lama_inpainting/utils/util.py:47-51].
**How to avoid:** Accept it (D-07 mandates edge clamping — the mask is fully included, which is the priority); the artifact at the extreme border is visually minor. Do NOT "fix" it by deferring edge masks (explicitly forbidden by D-07).
**Warning signs:** None needed — expected behavior; just don't let a later "cleanup" violate D-07 by deferring edge masks "for symmetry".

### Pitfall 5: The overlay/auto-plane semantics shift silently
**What goes wrong:** After the flip, the auto plane holds only the **inpaint-eligible** half (high-std + always). Users who relied on the red overlay to see "everything C will touch" see a shrunken overlay, and fill-only content is invisible on the mask layer.
**Why it happens:** Fill applies at Inpaint time only (D-03) — it is not a mask-plane member.
**How to avoid:** Carry the will-fill signal in the 5-state border pens (the discretion mandate) and update the threshold control tooltip (currently "Boxes above this are skipped (dashed border)" — tools_panel.py:461-466) to say boxes **above** are AI-inpainted and at/below are color-filled.
**Warning signs:** A user reports "C doesn't clean my boxes anymore" on a page where every box is below the threshold (all will-fill, empty inpaint mask) — the worker must still run the fill and only skip LaMa.

### Pitfall 6: The `"fill"` override value leaks through unmigrated validation layers
**What goes wrong:** `project_io.json_to_pagebox` rejects it (project_io.py:299-304), the Inspector maps don't know it (`_INPAINT_DISPLAY`/`_INPAINT_ITEMS` at inspector_panel.py:188-190), and `_INPAINT_OVERRIDE_TO_MODEL` (main_window.py:3745) drops it.
**Why it happens:** Three separate vocabulary tables were built for the Phase 8 tri-state (`None`/`"always"`/`"never"`), each hard-coded.
**How to avoid:** Change all four sites in one task: project_io loader, Inspector display/items maps, MainWindow commit map, and the `compose` branches (§Pattern 1). Add a round-trip test for a `"fill"` box through `.mas`.
**Warning signs:** A box set to Fill in the Inspector reverts to Auto on save/load — the loader threw `ProjectFormatError` or the display map fell back to "Auto".

### Pitfall 7: Fit-time median color vs recompute divergence
**What goes wrong:** If the fill recomputes `border_std_deviation` on the box-cropped mask at Inpaint time, the sampled border differs from the reference-frame border the fit used — a near-white bubble can get a grey-ish fill or a color mismatch vs what the std gate "saw".
**Why it happens:** `border_std_deviation` samples the FIND_EDGES contour of whatever mask it is given; the fitted mask's contour in the reference frame is not identical to the box-cropped one.
**How to avoid:** Store `median_color` at fit time (`BoxMaskFit.median_color` from `MaskFittingResults.median_color` [image_ops.py:706-719]) and carry it through the snapshot; the off-white rounding is baked in (image_ops.py:535-536).
**Warning signs:** Fills on uniform bubbles come out 2-3 RGB levels off from the surrounding white — the color was recomputed, not stored.

## Open Questions

1. **Which profile section owns `max_inpaint_resolution`?**
   - What we know: the tools dock already reads/writes `MaskerConfig` fields (`masker_values()`/`set_masker_values()`, tools_panel.py:569-627) and the `mask_dilation_radius` marked-addition precedent exists (config.py:564-569); `InpainterConfig` is vendored but app-unused.
   - What's unclear: MaskerConfig (recommended — least wiring, matches UI) vs InpainterConfig (semantically cleaner — it IS the inpainting section, and this key would be its first app use, following the same marked-addition pattern with `export_to_conf`/`import_from_conf` at config.py:838-927).
   - Recommendation: MaskerConfig, mirroring `mask_dilation_radius` exactly (field default 2048, `Pixels` type, INI export/import, `try_to_load` fallback). This is reversible if the user prefers the Inpainter section.

2. **Auto-plane display semantics after the flip (inpaint-only vs union)?**
   - What we know: D-03 says fill applies at Inpaint time; the LaMa mask = the inpaint-eligible composite; the 5-state borders carry the will-fill signal.
   - What's unclear: whether the auto plane should carry ONLY the inpaint-eligible content (recommended — it IS the LaMa mask, so the worker composite and the display agree) or BOTH halves (display shows everything C touches, but then the worker must re-split the plane by per-box data, and the fill content is never fed to LaMa).
   - Recommendation: inpaint-only in the auto plane; border pens show will-fill. Note it explicitly in the plan so the UI spec pass can confirm the overlay behavior.

3. **Batch Clean (mode only) over pages with NO per-box fit data (legacy `.mas` or never-detected pages)?**
   - What we know: batch clean reads `page.mask`; the fill needs per-box (mask, std_dev, fill_color); detect_and_clean always has fits from the same run.
   - What's unclear: what a clean-only batch should do for pages whose `.mas` predates per-box fits — fall back to today's whole-mask LaMa (recommended: strokes and legacy content still get cleaned, and it matches D-01 "hand strokes always inpaint"), or skip clean with a logged message.
   - Recommendation: fall back to whole-mask LaMa for pages without fit data; apply the corrected gate+fill+patch only when per-box data exists. This preserves FLOW-03 on legacy projects.

4. **Threshold boundary equality (`std == threshold`)?**
   - What we know: D-01 says "at or BELOW the threshold → fill; ABOVE → inpaint"; the current compose uses `std_dev <= threshold` for the gate-passing side.
   - What's unclear: nothing semantically — the flip keeps `<=` for fill and uses `>` for inpaint (exactly PanelCleaner's `> mask_max_standard_deviation` fail condition).
   - Recommendation: `compose_fill_binary`: `std_dev <= threshold`; `compose_auto_binary` (inpaint half): `std_dev > threshold`, mirroring image_ops.py:705. Equality is rare (float std); pin it with a boundary test.

### Known Threat Patterns for the stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Oversized input DoS (a huge page or a crafted patch rect allocating huge buffers) | DoS | The D-05 max-size cap + strict int dims validated before numpy/PIL allocation (T-05-06 discipline); patch rects derived from mask bboxes, never from model output |
| Malformed project data (`"fill"` value in an old `.mas`, or a garbage override string) | Tampering | `json_to_pagebox` structural validation widened deliberately to accept exactly `"fill"` and reject anything else (`ProjectFormatError`) — the T-08-08 format-version stance; legacy files load unchanged |
| Model-weight tampering / missing file | Tampering | Unchanged existing guards: `load()` path check before torch import (torch_impl.py:216-227, T-01-04b); no new model loading in this phase |
| Worker-thread crash from a malformed patch crop | DoS | Patch math is pure numpy/PIL with bounds checks; the per-page `try/except` in the batch loop (batch_runner.py:242-245) and the Worker error signal keep a bad page non-fatal |

### Data-integrity class (T-08-10-01..05 continuity)
The patch compositing and the single-undo-entry contract are data-integrity operations: a never-pasted patch or a duplicated undo push would corrupt the page or the stack. The phase inherits 08-SECURITY.md's threat register and adds: **T-08.1-01** patch-coverage completeness (every inpaint-eligible pixel is inside at least one patch rect — asserted by the planner tests), **T-08.1-02** single-push undo (the worker returns one bbox; the finish handler pushes once — guarded by the existing push-site shape), **T-08.1-03** .copy() detachment on every numpy↔QImage bridge in the new flow (Pitfall 2, the `test_inpaint_result_display_uses_copy` regression pattern) and on the union-bbox pre-patch slice.
